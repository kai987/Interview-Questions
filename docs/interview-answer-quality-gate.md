# 面接回答の品質ゲート（題庫追加・改稿用）

質問数、文字数、保存成功だけを完了条件にしない。回答の内容と、実際に口頭で話す順序を確認する。

## 3段階回答の役割

| 版 | 目的 | 練習時間の目安（録音の実測ではない） |
| --- | --- | --- |
| `short`（結論） | 単独でも質問に答えられる短い回答 | 15～30秒 |
| `standard`（標準） | 経験・行動・結果を含む一次回答 | 45～80秒 |
| `full`（深掘り） | 判断理由、技術詳細、検証などを加えた独立した回答 | 80～150秒 |

時間は話す速度と質問による。年収、入社日、逆質問を文字数のために引き延ばさない。実測していない時間を録音時間として表示しない。

## 質問に合わせた順序

すべての回答に、同じ「結論の段落」を付けない。短縮版は独立した回答であり、標準版の前に連結する部品ではない。

| 質問の種類 | 話す順序 |
| --- | --- |
| 自己紹介 | 氏名・挨拶 → 主な実務経験 → 代表プロジェクト・技術 → 現在の学習 → 志望方向 → 結び |
| 来日・志望理由 | 直接の理由 → 背景 → 関連する経験 → 今後の方向 |
| 成功・失敗・難問 | 対象・状況 → 課題 → 自分の行動 → 確認できる結果 → 学び・再発防止 |
| 対応手順・技術設計 | 前提・目的 → 実行順の手順 → 判断の理由・例外 → 検証・効果確認 |
| 会社別の職務 | A社の説明を完結 → B社の説明を完結 → 必要なら比較・活用 |
| 年収・入社日 | 金額・日付への直接回答 → 必要な条件 → 相談の結び |
| 逆質問 | 質問を受ける → 実際の質問を一つずつ → 必要なら聞く目的 |

「活かしたい」「学びました」「よろしくお願いいたします」で締めた後に、再び同じ経験説明へ戻らない。深掘り情報は結びの前へ配置する。

## 内容チェック

1. 実務、大学院、個人開発、想定提案を区別する。実験したことを製造現場での商用運用と混同しない。
2. 個人の役割、行動、確認できる結果を具体的にする。改善率、退職事情、未確認の経験を創作しない。
3. 技術質問は単語の列挙で終わらず、データ、処理、判断基準、確認方法を示す。
4. 古い回答へ追加段落を連結するだけの改稿は禁止。同じ内容の言い換え、時系列の往復、早すぎる締めを全文で確認する。
5. 話す本文へ「面接前に確認」「本人が差し替え」「この例を使う」などの練習指示を混ぜない。指示と未確認事項は `outline` に置く。
6. 未確定の希望年収などの入力欄は三版で統一し、未確定であることを `outline` に記録する。
7. `full` は `standard + 補足` と機械的に作らない。共通の本論へ詳細を差し込み、最後に結びを置く。三版をそれぞれ独立して読む。
8. 逆質問は同じ質問を要約と本文で二度尋ねない。時間に合わせて候補を選ぶためのメモを本文から分離する。

## DB反映のチェックリスト

- 個人用回答は本人限定の `interview_private_content` に保存し、公開Gitへ掲載しない。
- `answer` と `answer_variants.standard` を同期する。表示中の版はUI側で正しく選択する。
- 対象の題庫と所有者を絞り、読み取った `updated_at` と一致する行だけを更新する。不一致は停止して再確認する。
- 対象以外の回答、問題ID・設問文、題庫、`interview_user_state`、RLSを変更しない。
- 既存音声がある場合は本文ハッシュの不一致を確認し、必要な再録音は別作業として扱う。時間や音声情報を捏造しない。
- 全文の順序を読む。機械検査は補助であり、意味上の重複や話しやすさの保証にはならない。
- 改稿前後で、題目・他社回答・学習状態など対象外データが保持されたかを比較する。

## 読み取り専用のQA例

```sql
with answers as (
  select q.sort_order, pc.answer, pc.answer_variants
  from public.interview_sets s
  join public.interview_questions q on q.set_id = s.id
  join public.interview_private_content pc
    on pc.question_id = q.id and pc.user_id = s.owner_id
  where s.slug = 'micron-japan-production-dx-jr88130'
)
select
  count(*) as questions,
  count(*) filter (
    where answer_variants ? 'short'
      and answer_variants ? 'standard'
      and answer_variants ? 'full'
  ) as three_versions,
  count(*) filter (
    where answer = answer_variants->>'standard'
  ) as default_synced,
  count(*) filter (
    where starts_with(answer_variants->>'full', answer_variants->>'standard')
  ) as appended_after_entire_standard
from answers;
```

`appended_after_entire_standard` は一律エラーではなく、標準版の結びの後へ補足を足していないか調べるための指標。本人がアクセスできるアカウントで実行する。

## 表示版の回帰検査

`app.js` はカードの初期描画に `item.answer` を使い、`answer-variants.js` の初期選択は `full`。そのため、標準と深掘りが異なる場合は、初期描画でも選択中の版へ正文を同期する必要がある。

`tests/e2e/answer-variants-order.spec.mjs` は個人情報を含まない合成データを使い、次を確認する。

- 初期の「深掘り」選択と本文・読み上げ対象テキストの一致。
- 結論／標準／深掘りの切り替えと、一つだけが選択されること。
- カード再描画後も、初期の深掘りまたは選択済みの結論が保たれること。
- 深掘り未登録時の既定本文へのフォールバックと、同じ本文に付いたハイライトの保持。
- 個人用本文のないカードに、回答や版コントロールを追加しないこと。

```bash
npx playwright test tests/e2e/answer-variants-order.spec.mjs --project=desktop --project=mobile
```

## 2026-10-08 Micron題庫の是正記録

初回は回答の存在だけを確認し、内容が薄いまま反映した。その後の増補でも、旧回答の後ろに説明を足したため、同じ経験の反復、早すぎる結び、自己紹介の挨拶不足が残った。文字数の増加だけでは解決しなかった。

今回、35問の標準版・深掘り版を質問の種類に合わせて再構成し、短縮版も整合性を確認した。深掘りの詳細は結びの前に配置し、話し方の指示は本文から分離した。個人回答そのものはGitに含めない。

DB検査：35問・105個の非空バージョン、既定本文と標準版の一致35件、標準版と深掘り版の最終段落の一致35件、標準版の全体末尾へ説明を足した構造0件、完全一致する重複段落0件、対象の練習指示パターン0件。自己紹介は三版とも氏名から始まり、挨拶で終わる。これらは意味・自然さの全文確認を補助する検査。

変更前後の比較で、設問データ、題庫、他社の回答、学習状態、RLSの保持を確認した。Micronの既存録音は0件で、録音生成は行っていない。

表示側は初期版の不一致を再現して修正。Browserプラグインがこの環境にないため、Python PlaywrightとシステムChromiumを使用した。localhostへの遷移はブラウザポリシーでブロックされたため、ブロックされたURLへアクセスせず、オフラインの合成HTMLでモジュールを検証した。1440×1000と390×844で初期表示、三版切替、再描画、フォールバック、ハイライト、未解除カードを確認し、関連するコンソールエラーはなかった。

このローカル検証は、本番ログイン、Supabase通信、実際の音声再生、サイト全体のE2E合格を意味しない。追加したE2Eファイルは既存のテスト構成で実行できるようにしたが、ここで実行したのはオフラインの対応検証である。
